## 已发现并复核修复的问题

| 级别 | 问题与复现 | 修复与复核 |
| --- | --- | --- |
| P1 | 原生 `Action → Emit` 给 `hostAction` 添加 `targetInstanceId/generation`，并给普通动作添加 `options:null`。严格 Node 解析器全部拒绝，任何设置/登录操作都会触发后台关闭。内存编译协议并输入实际旧 envelope，得到 `actualNativeEnvelopeAccepted:false`，标准 envelope 为 true；原有单元测试仍全通过。 | `Action` 改用独立 envelope，普通动作省略 options。读取真实 C#→Node smoke 结果文件为 passed:true；另独立运行 Node bundle 设置变更，收到 ok:true，并读回 ja、autoTranslate:false、shortcutEnabled:false、followCustomerLanguage:false。 |
| P2 | `StartChild` 在 `Start()` 和读管道之后才注册 `Exited`，快速退出可能丢掉事件，有限重试失效。 | 事件注册前移至 Start 前，采用 Interlocked 去重；源码复核通过。此结论包含源码验证，未将其描述为独立执行的 C# 快速失败故障注入。 |
| P2 | 原性能采样把显式启动的厂商后代同时计入 helper 和 vendor；宿主退出后也可能跟随复用 PID。 | helper 排除显式 vendor 树，采样循环核对宿主启动时间。源码复核通过。既有与助手无父子关系的 vendor 基线不受双算问题影响；具体正式统计仍以原始日志和场景为准。 |
| P2 | UI 线程同步写 Node stdin；Node 不读且管道积满时，退出会在发送 quit 阶段卡住，10 秒等待无法保护此调用。同时 stdout 每行 BeginInvoke 原先没有排队上限。 | 改为容量 64 的异步写 Channel、每条 3 秒超时；退出先标记 quitting，写队列至多等待 1 秒，关闭底层流，等待后台至多 10 秒并仅 Kill(false) 自有 Node；读端 UI 排队上限 128。独立故障注入复核约 12.8 秒退出，详见下文。 |

## 早期默认 V8 堆模式内存增长的只读分析

独立读取当时的 `resource-summary.json` 与两份原始空闲采样：早期未限制新生代的轻量宿主单轮 10 分钟助手私有提交 p95 为 210.203 MiB、峰值 264.195 MiB，高于 Electron 基线 p95 196.297 MiB；工作集合计 p95 从 337.566 降至 257.934 MiB。**旧版采样的 CPU 差值存在整数重载取整，先前“平均 CPU 低于 0.01%”的引用已废弃，不能用于比较或验收。** 该轮未达到计划中的私有提交资源门禁；工作集下降不能替代该项。最终包默认参数后来改变，不能把该历史数据当作最终默认包的实测数据。

轻量宿主预热后 265 个 helper 样本始终为 3 个进程：Resident、Node、conhost，没有采到 PowerShell。第 1 至第 9 个完整稳态分钟的私有提交 p95 约为 139.6、144.6、154.9、153.1、157.3、179.8、172.8、207.9、264.0 MiB，后段上升真实存在。当前采样只记录树合计，不能判定增长属于 CLR、Node、conhost 或其他分配类别。

检查 `runtime/transport.ts`、`driver.ts`、`cdp-policy.ts`、`companion-service.ts` 与认证调用链，结论分为以下几类：

1. **未发现正常请求的 pending/监听器线性保留。** transport 在结果到达时删除 pending 并清 timeout，超时断开时清所有 pending 和监听器。独立内存 FakeSocket 连续 10,000 次合法请求后，pending=0/events=1/disconnects=1；断开后 pending/events/disconnects/socketListeners 全为 0。此实验不证明真实 WebSocket 底层实现没有缓冲保留。
2. **未发现每次空闲 poll 新增远程对象句柄。** poll、heartbeat、状态发布均 returnByValue:true；初始化 factory/native/ui 使用固定 contextNonce objectGroup，detachSession 释放该组；临时 DOM 句柄有 finally release。scripts Map 只接收固定 renderer URL，defaultContexts 只接收当前主 frame 的默认上下文；通常各一项。其未显式清空本身不能证明泄漏，因为断开已解绑 transport 监听器并释放整个 driver。
3. **认证缓冲区反复分配是待量化嫌疑。** 连接时后台每 4 秒 sync，单 flight 防止重叠；成功路径在 profile 核验前后各 tokenAt 一次。每个 tokenAt 的 LevelDB attempt 保留 observed 文件 Buffer，逐个完整复读确认一致性，再复查控制文件；单文件 64 MiB、累计 256 MiB 是安全上限，并非实测文件大小。没有发现 Buffer 逃逸到跨调用缓存的路径，因此更像可能的 external/arrayBuffers 分配高水位，尚未证明持续保留。不能删除复读、忽略删除记录或缓存旧 token 来降低数字。
4. **主 IM Debugger 持续开启是待测分配/厂商保留嫌疑。** enableInspection 开启 Debugger 后只在整个会话 detach 时结束；导航 session 的临时 Debugger 在脚本校验后显式 disable。主会话频繁 callFunctionOn/evaluate 期间可能继续产生 scriptParsed 事件，transport 仍会 JSON.parse 并交给 driver 过滤；只保存固定 renderer URL 的 Map 不能消除事件分配。若评估在初始化所有脚本/父监听核验后停用 Debugger，需要保持原有构建指纹、会话/上下文及目标验证并补实际回归，不能直接放宽验证。
5. **其余已检查队列具有合并或时间边界。** 观察用 busy/renewing，嵌入发布用 dirty+单任务，native 事件用 wake+单 drain；认证 syncing 单 flight，active 请求 finally 移除。请求 AbortSignal timeout 最多保留到超时期限，数量有频率边界，不足以仅凭源码说明 10 分钟后段增长。

后续诊断应先分别记录 Resident/Node/conhost 的数字资源，Node 记录 heapUsed、heapTotal、external、arrayBuffers、rss，以及 CDP pending/订阅计数；比较增长归属后再选优化路径。本审查未对真实进程强制 GC、裁剪工作集、改变认证或操作客户端。compact-heap 只能作为明确标注的可选 A/B，不代表已找到根因或达到默认模式门禁。

## CPU 计量缺陷与旧数据废弃

主代理发现采样脚本旧表达式 `[Math]::Max(0, delta)` 选择整数重载。审查者分别在 PowerShell 7.4.6 和 Windows PowerShell 5.1.26100.9711 独立复现：Max(0,0.125)=0；显式 double 后为 0.125。另 Max(0,0.75)=1，因此旧数据不只是漏掉小值，也可能向上取整，无法用统一系数修复。

当前 `measure-resident.ps1` 已改为 `[Math]::Max([double]0,[double](delta))`，累加器也保持 Double，差值不再经过整数重载。内存累计使用 Int64 字节，除以 1MB 后为 Double；独立验证 1310720 字节得到 1.25 MiB，未发现同类内存取整。Stopwatch.TotalSeconds、区间 dt 与 CPU 归一化计算均保留浮点数。

影响范围：使用旧表达式采集的 Electron baseline、默认轻量宿主，以及已开始且脚本已加载的 compact 模式，其全部 CPU 均值/p95/峰值和 CPU 优劣结论作废，修改磁盘脚本不会修复正在运行的旧脚本实例。这些文件中的内存、进程数和句柄数据不受本缺陷影响；不得为了重测 CPU 丢弃有效的 600 秒内存记录。现有旧样本没有原始累计 CPU，因此不能从旧 cpuPercentMachine 还原精确差值，需要重新采集。

另已报告的计量事项：

- `summarize-resident.mjs` 原先对每个区间 CPU 百分比做算术平均，而实际枚举间隔不等。已修为 sum(percent*duration)/sum(duration)；每组先按全部相邻 seconds 求 duration，再筛选预热后的样本，因此保留了第一个稳态样本的正确前置时间点。独立算例：1 秒 100%、随后 9 秒 0%，算术均值是 50%，正确时间均值为 10%。本次增量完成源码复核，没有另跑测试或启动宿主。CPU p95 仍为采样点分位数，应按该口径理解。
- 新采样已标记 measurementVersion=2；汇总对版本小于 2 或缺失的样本返回 cpuPercentMachine.valid:false，并给出旧重载原因，不再输出旧 CPU 均值/p95。现有旧文件没有该标记，不能被新算法“洗成有效数据”。后续可额外保留原始 deltaCpuSeconds/intervalSeconds 便于审计，但不影响当前版本失效标记修复。
- 离散快照会漏采短命后代；新出现进程的首次样本没有前值时当前 CPU 差值为零，即使采到它也可能漏掉其此前消耗。进程树按 PID 递归，厂商根 PID 尚无与 helper 同等的启动时间校验，CreationDate 当前未用于父子时间关系排除；长期退出/重启或 PID 复用场景应标记测量无效或增强身份跟踪。
- 汇总的 peak 取自预热后样本，是稳态峰值；启动/连接峰值仍需单列。独立检查本轮两份现有内存原始日志，整段最高值与预热后最高值恰好相同，没有因此漏掉这两轮已观察到的最高值。

源码检查结果：

- HasExited/MainModule 使用同一持有的 boundProcess；绑定时取 SafeHandle，失去目标、解绑、后台退出与应用退出均 Dispose。窗口枚举及 WinEvent 临时 GetProcessById 均用 using；未找到每次监测明确留下一个 Process 对象的路径。

- BeginInvoke 排队数量已设上限，调用处没有读取返回 IAsyncResult 的 AsyncWaitHandle；不能仅凭调用 BeginInvoke 把增长归因于等待句柄。ReadBounded、WriteOutput 与 UI 调度涉及运行时异步协作，线程池扩张/管道适配是候选，但本轮没有线程栈或句柄类型证据，无法确认。
- 显式 openLogin 的 Process.Start 返回值没有在当前调用中 Dispose，可能依赖后续回收；该路径只有显式打开登录时执行，不符合纯空闲每 30 秒持续增长的触发条件。它是可改进的确定性清理点，不是本轮空闲增长的已证明根因。
