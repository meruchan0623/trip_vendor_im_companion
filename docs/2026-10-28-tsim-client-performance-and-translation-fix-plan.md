# TSIM 旅游商家客户端卡顿与翻译兼容修复计划

日期：2026-10-28

状态：仓库修复及 0.7.4 候选包已完成，自动化与隔离检查通过；尚未安装到用户客户端。详见 [实施与验收记录](2026-10-28-tsim-injector-0.7.4-validation.md)。

交付目标：将助手侧的翻译兼容、错误展示和性能修复合入同一个 macOS 一次性注入安装包，由用户在安装器界面主动安装或更新。

## 1. 结论与范围

当前问题由几类原因叠加：助手发送了旧服务端不接受的翻译字段；助手自动加载隐藏订单工作台并执行重复页面读取；官方页面也存在秒级主线程长任务；系统内存压力与旧版 x64 运行时可能进一步放大卡顿。不能把所有问题归因于 Electron 版本，也不能根据整机 CPU 未跑满判断页面没有性能瓶颈。

本轮优先修复可以由注入包独立完成的部分，不将升级 TSIM 服务端、另装浏览器扩展或更换官方 Electron 作为 macOS 修复的前置条件。官方代码中已经观察到的长任务继续保留为整体验收问题；只有真实复测通过，才可宣称输入、复制、滚动和会话切换问题已经解决。

统一使用“TSIM”描述产品、账号、诊断结果和用户可见错误。原始日志及采样证据保持原样；实现时在展示层兼容历史内部错误前缀并转换为 TSIM，不通过全局字符串替换改变既有账号作用域、存储键、IPC 协议或登录态。

实施边界：

- 最初计划阶段只新增文档；后续按用户授权实施。开发、构建及安装事务测试限于仓库和隔离临时目录。
- 不直接修改、替换、修复或卸载已安装客户端；不自动执行安装器写入。安装、更新和恢复由用户主动操作。
- macOS 继续使用助手内独立 TSIM 登录，不读取 Chrome、Edge 或其他应用的 Cookie、登录态。
- 不修补官方 macOS 窗口生命周期、BrowserView 挂载或渲染节流；仅保留助手运行所需的入口集成。
- 不屏蔽、替换或伪造官方环境检测、风控及其他安全相关脚本的结果。

## 2. 已有证据与尚未证实的判断

以下数据来自本机真实操作采样，时间为 UTC+08:00。它们是修复依据，不是改进后的验收结果。

| 项目 | 已确认的观察 | 对修复决策的含义 |
| --- | --- | --- |
| 运行环境 | 官方客户端 1.2.12，Electron 27.3.11 / Chromium 118，x64 经 Rosetta 运行；助手采样版本 0.3.2、注入包 0.7.0，助手 Electron 44.7.2 / Chromium 152、arm64 | 助手的较新 Electron 不会升级官方页面所在的旧运行时；官方运行时更新需官方支持 |
| 第一轮交互 | 12:01:35–12:03:38，约 123 秒，130 个长任务，合计约 26.9 秒；最长约 1.805 秒；捕获到的 keydown 时长最高约 3.08 秒 | 卡顿真实存在，重点检查主线程排队与执行，不能仅看进程平均 CPU |
| 翻译失败 | 三次 `/agent/translate` 返回 422，耗时约 166–187 毫秒；已安装助手发送 `client_source`，实际服务端模型禁止额外字段且未声明该字段 | 存在确定的协议不兼容。用实际服务端模型及合成输入离线复现 `body.client_source / extra_forbidden`；未取得这三次响应的具体 detail，不能把每个 422 都归为同一原因 |
| 自动预热 | 助手预热回调约 68.4 毫秒；后续同 renderer 的 TSIM React 回调约 265.8 毫秒 | 自动创建不可见的完整工作台仍产生计算开销。后一个回调不能全部算作前一个回调的执行时间 |
| 订单扫描 | CPU 采样确认 `isOrderSourceVisible` 祖先样式读取及订单读取链为助手热点 | 优先减少重复扫描和样式查询；函数累计采样耗时不能直接当作单次任务时长 |
| 摘要定位 | 65.6 秒 trace 内 `place` 131 次，总计约 182.7 毫秒，最大约 18.4 毫秒；存在强制样式计算路径 | 值得优化重复布局，但不是本次秒级卡顿的充分解释 |
| 语言扫描 | 同段 trace 内 7 次，总计约 20.6 毫秒，最大约 7.0 毫秒 | 有缓存优化空间，尚无证据表明语言识别是主要根因 |
| 输入与复制 | 第一轮输入相关助手快照更新累计仅数毫秒；第二轮三个 copy 事件约 0.181、7.120、0.225 毫秒 | 未证实助手复制处理或每次输入序列化是主要根因；复制体感卡顿可能来自此前主线程阻塞，须用完整时间线验证 |
| 官方页面 | 第一轮约 1.47 秒任务含 React DOM 提交、节点增删与滚动；第二轮官方 `bn-pf` 单次调用约 2.59 秒；官方粘贴处理约 173 毫秒 | 注入包只能先消除自己增加的工作，不能把官方重任务直接计入助手修复收益 |
| 内存与 CPU | 系统出现内存压力警告、约 8–9 GB 压缩内存及约 2.2–2.8 GB swap；交互时目标 renderer CPU 峰值约 120%，整机未持续满核 | 内存压力是影响因素；DOM、布局和多数页面脚本仍共享主线程，空闲 CPU 核不能自动分担这些工作 |

证据限制：

- 第二轮发生 renderer 更换，用户感觉卡顿减轻不能视为同条件 A/B，也不表示问题自行修复。
- 第一轮事件时长采集有阈值过滤，不能直接当作全量交互的 p95/p99 分布。
- CPU profile 存在时间戳异常及未归因原生执行；函数采样估算、wall time 和线程 CPU 时间要分别报告，inclusive 时间不能直接相加。
- 没有证明长期内存泄漏、助手重复实例同时存活或 MutationObserver 无限自触发。多个先后加载的相同脚本也不能单独证明重复注入。
- 没有旧版与新版官方 Electron 的受控对照，因此不承诺升级框架即可解决全部卡顿。

## 3. 单一注入包的交付设计

一次安装包含同版本的助手应用、页面运行时、输入适配、入口 bootstrap、兼容配置及必要诊断。用户不需要手工替换脚本或串行安装多个热修复包。

| 包内组成 | 负责解决的问题 | 约束 |
| --- | --- | --- |
| 翻译兼容与错误规范化 | 当前旧服务端字段不兼容、将 422 错报为连接问题 | 默认使用已验证兼容的请求字段，不依赖服务端先升级 |
| 页面调度与订单工作台 | 自动完整 SPA 预热、重复订单扫描、摘要定位 | 不改变官方窗口与渲染机制 |
| 助手实例及资源管理 | 切会话、重载、重新挂载后的资源残留防护 | 作为回归和健壮性要求，不能表述为已证实存在重复注入 |
| 轻量诊断 | 核验实际加载版本、运行时哈希、调用数和失败分类 | 默认不持续 CPU tracing，不记录聊天正文、译文、令牌或 Cookie |
| 安装与恢复 | 一次更新全部助手组件，失败可恢复 | 复用现有备份、收据及事务机制，由用户在界面触发 |

“一个包”以本次 macOS 客户端为交付对象。公共代码需保持 Windows 兼容；Windows 如需发布，应由对应平台安装包交付，不承诺一个二进制覆盖两个系统，也不改变其现有登录方式。

## 4. P0：恢复翻译兼容并修正 TSIM 提示

### 4.1 首次请求就兼容旧服务端

当前代码没有可信的事前能力信号证明服务端接受 `client_source`。账号权限、`outbound_wait`、助手版本和成功响应里的协议标记都不能替代该能力声明。

单条出站翻译默认按白名单构造请求：`text`、`target_lang`、`source_lang`、`purpose`、`draft_request_id`、`composer_content_version`。不额外发送 `client_source`，不擅自补入新的协议字段。保留草稿 ID、内容版本、会话隔离、取消和防陈旧结果逻辑。

需要同步处理的已有出口：

- `host/owned-service.ts`：macOS 助手独立会话出口，是本次单包修复必需项。
- `electron/browser-profile-session.ts`、`browser-extension/background.js`：保持公共翻译约定一致；macOS 修复不依赖用户另装扩展。
- `host/runtime.ts`：单条出站路径保持原协议；入站批量路径继续使用自己的 `texts` 等字段，不能套用出站六字段。两条路径均不新增来源字段。

不采用“任意 422 后删字段自动重试”。422 也可能来自其他校验或上游服务，盲重试会掩盖原因并可能重复调用、重复计费。后续只有服务端提供明确且已验证的能力声明时，才可在第一次请求前决定携带来源字段；该增强不阻塞本次发布。

兼容模式暂时无法通过这个可选字段为服务端新增插件来源统计；本地仍可记录安全的来源标签。更新 README 中当前“先升级后端、再更新助手”的发布说明，明确这是有意变更的兼容策略，而非无声回退。服务端升级可恢复更细统计，但与本次恢复翻译分开验收。

### 4.2 错误分类与显示

在 `host/owned-service.ts` 的 HTTP 层读取有大小上限的错误响应，仅提取白名单字段，例如 HTTP 状态、可信请求 ID、校验位置及错误类型。禁止将响应中的 `input`、聊天文本、原始异常、完整响应或凭据直接透传到 UI、日志及遥测。

在 `electron/companion-service.ts` 统一映射用户提示：

- 401、423：根据既有契约处理登录失效或账号锁定，不能仅提示检查网络。
- 403：权限不足；保留服务端实际权限判断。
- 422 且明确为字段校验：请求格式或客户端兼容问题，显示安全摘要。
- 422 但原因未知：请求未被服务接受，保留状态码与诊断编号，不猜测网络或权限。
- 429：请求过于频繁；5xx：服务暂不可用；超时或断网另行分类。

同时检查 `electron/browser-profile-session.ts`、`browser-extension/background.js` 及订单摘要把 422 映射为权限不足的路径。错误体缺失、超限或无法识别时退回准确的状态码提示，不阻塞翻译兼容修复。所有用户可见产品名、错误前缀和文档统一 TSIM；历史内部代码先兼容识别，再映射显示。若未来需要改账号作用域或持久化键，另设可回滚的数据迁移，不混入本次文案更正。

完成标准：旧模型 `extra='forbid'` 的合成测试通过；新版模型兼容；每次用户翻译仅产生预期的一次业务请求；未知 422 不重试、不泄露错误输入；真实翻译成功且来源统计降级已被说明。真实业务请求只使用用户主动触发的翻译验证，不为探测能力额外发送消息或翻译。

## 5. P0：取消自动加载完整订单工作台

主要文件：`runtime/page/index.ts`、`runtime/page/operator-overlay.ts`、`tests/operator-overlay.test.ts`。

去掉登录就绪或订单 chip 变化后自动创建完整隐藏 SPA 的默认路径。用户首次点击订单查询时再初始化工作台；显示加载状态，继续使用助手独立会话与现有授权握手。首次打开变慢的可能性必须单独测量，不能以牺牲输入响应换取未点击功能的预加载。

轻量连接预热只有在确认目标确实轻量、未启动完整 SPA 且有可测收益时才保留；否则一并关闭。不要仅把 1.2 秒预热改成另一个固定延迟，也不要把同样的重任务移到 `requestIdleCallback` 后当作问题已解决。

用户已打开的工作台可短时复用，但需设定明确的释放策略：关闭后有限保留，超时销毁；切换账号、授权失效、宿主页面卸载时立即释放；切会话后不得显示旧订单。关闭后仍运行的远端页面若无法可靠暂停，就通过销毁 iframe 释放，而非假定 `visibility:hidden` 等于停止执行。建议初始保留上限 60 秒，在真实复测后确定最终值。

完成标准：登录后未点订单查询时没有完整 TSIM 工作台 iframe；输入、复制、滚动和切会话不会触发自动完整页面预热；首次及再次查询均可用；过期授权、退出、关闭再打开、请求乱序无旧订单闪现或账号串用。

## 6. P1：减少订单观察与摘要布局占用

主要文件：`runtime/page/index.ts`、`runtime/page/identifiers.ts`、`runtime/page/order-summary-card.ts`。

### 6.1 订单读取按变化触发

- 将全页变动筛选为会话标识、订单 iframe、订单字段及相关可见性变化；保留页面结构被整体替换时的有界重新发现路径。
- 缓存当前会话及已验证订单节点；每轮读取复用共同祖先的可见性结果。会话切换、节点移除、iframe 导航或相关样式变化必须失效，不能长期缓存导致读错订单。
- 同一批 MutationObserver 通知只安排一次扫描；有待执行扫描时不重复排队。非紧急扫描避开输入组合阶段，设最大延迟避免一直输入时订单永不更新。
- 会话、订单值和授权均未变化时，不重复更新摘要数据。切换时先清除旧绑定，再接收新会话结果；不能为提速删除来源校验或多候选拒绝逻辑。

### 6.2 摘要定位按几何变化触发

当前已有 `ResizeObserver`、滚动监听及 rAF 合并，应在其基础上减少无效触发，而非重复增加一组监听器。

- 将摘要数据更新与几何更新分开，避免 `renderCurrent(true)` 在确认绑定未变化前仍重复 `syncSummary`。
- 缓存 iframe 和相关布局节点；仅在绑定、大小、滚动、视口或摘要内容高度改变时测量。
- 每帧先集中读取几何，再写入真正变化的 style。避免写 style 后立即调用 `getBoundingClientRect` / `elementFromPoint`；堆叠关系确需检查时另设有界时机。
- 缩放、窗口 resize、侧栏变化、iframe 重载和用户信息区域滚动仍需正确定位；不可遮挡官方对话框或订单内容。

完成标准：稳定空闲时不因无关 DOM 变化持续扫描或定位；助手订单观察不再产生大于 50 毫秒的长任务；订单及时刷新、摘要位置正确，切会话与乱序结果测试无回归。

## 7. P2：降低剩余后台开销并保证输入安全

### 7.1 客户语言识别

在 `runtime/page/language.ts`、`runtime/page/index.ts` 中缓存当前会话的客户原文窗口指纹，仅当原文、归属或可见性发生相关变化时重新检测。保留当前最多 30 条候选窗口及语言判定语义，避免把客服消息、译文附文、引用、序列号等误算为新证据。

这属于重复工作优化，本轮证据不支持把它描述为主要卡顿来源。先测量缓存命中和真实计算成本；只有纯计算持续超预算时，才考虑 Web Worker。DOM 查询和布局不能直接通过“多开线程”解决。

### 7.2 输入适配与实例清理

检查 `runtime/native-composer.ts`、`runtime/runtime-ui.tsx`、`runtime/driver.ts`、`electron/companion-service.ts` 的重复快照、心跳和资源生命周期。只对可测的重复工作合并或降频，保留租约续期、安全读回、中文 IME、草稿内容版本比较及发送前校验。

每个有效页面仅一个助手实例；重新挂载先清理自己的监听器、observer、timer、rAF、iframe 和失效请求。按页面生命周期统计资源数量，不以 scriptId 数量判断重复实例。会话变化后过期翻译不能替换新草稿；复制、撤销、粘贴、连续中文输入均须保留原行为。

不新增每键重扫描、长期完整 CPU profile 或高频全量诊断。诊断采用有界计数和显式短时采集，结束后可确认已停止。

## 8. 官方页面与运行时问题的处理

官方 `bn-pf` 长调用、React DOM 提交、粘贴处理及未归因原生主线程工作，列为整体卡顿的剩余问题。先确认助手是否诱发了额外调用，能够通过减少助手 DOM、iframe 或事件活动消除的部分纳入本包；不能消除的部分保留独立证据和复现步骤交给官方维护方。

不在本包中替换官方 Electron、不拦截官方脚本，也不通过重写官方 React、滚动函数或窗口策略掩盖问题。官方未来提供原生 arm64 或较新运行时版本时，再做相同动作与数据量的兼容及性能对照。升级收益必须由测量确认。

内存方面减少助手闲置 iframe、监听器及缓存持有，并设定缓存边界。不会通过强制垃圾回收、清空业务数据或全局关闭窗口达到漂亮指标。持续内存增长需用固定负载下的堆、DOM、资源计数与系统压力一起判断；当前采样不能证明泄漏。

若改完助手后仍有官方秒级长任务，交付说明必须写明“助手侧修复已完成，整机交互卡顿仍有剩余”，不得把一个安装包的交付完成等同于全部体验问题解决。

## 9. 单包构建、版本核验与恢复

复用 `scripts/package-macos-injector.mjs`、`native/macos-installer/` 及现有事务逻辑，所有新修复合入同一构建。实施时检查构建参数、README、manifest、助手内版本和日志版本一致；不直接沿用脚本默认版本，也不以 README 的版本号代替实际安装版本。

官方页面可能从 Application Support 中的动态资源加载。安装前的包内校验和运行后的真实页面校验必须分别完成；仅匹配 `app.asar` 中的静态 bundle 不足以证明修复已经加载。

交付内容与门禁：

1. 一个版本化的 macOS 一次性注入安装器 ZIP，内含完整助手及运行时；校验和与构建报告为附属验收材料，不是额外安装步骤。
2. manifest 记录组件摘要、实际验证的官方版本及构建信息。连接页面时核对实际加载来源、bundle 哈希和功能契约；未知页面结构停止不安全功能并给出兼容提示。
3. 在临时目录验证首次安装、旧助手更新、重复安装、官方重新安装后再注入、事务中断恢复、备份不完整和卸载恢复。保留既有原件备份与用户数据。
4. 使用同一安装器界面的“检查”“安装 / 更新”“卸载并恢复原版”完成用户操作；不附带要求用户手工复制文件、运行补丁脚本的流程。
5. 如需回到旧助手版本，须验证受支持的版本回退事务；“恢复官方原版”与“回退旧助手版本”分开记录，不能互相替代验收。
6. 记录真实签名与公证状态。现有打包逻辑为 ad-hoc 签名且未公证，未经实际完成不能标为已公证发布包。

## 10. 验收方法与通过标准

### 10.1 自动化与隔离测试

扩展现有 `macos-owned-session`、`translation-http-telemetry`、`translation-service-telemetry`、`operator-overlay`、`order-summary`、`macos-runtime-order`、`macos-native-parity`、`macos-dynamic-runtime`、`native-recovery`、`transport-recovery` 测试。`translation-http-telemetry.test.ts` 当前明确断言携带来源字段，需随兼容策略一起更新为旧、新模型均接受的请求断言。新增用例应验证行为与失败边界，不能仅复制实现或用 DOM 模拟器证明真实浏览器性能。

必测：旧后端未知字段拒绝、新后端可选字段兼容、422 分类与无自动重试、错误响应脱敏、取消及账号切换；无点击不创建 SPA、关闭后释放、授权更新；订单来源变化、iframe 重载、多候选订单拒绝、摘要几何；IME、复制粘贴、撤销、会话隔离、陈旧结果禁止写回。共享代码变更同时跑相关 Windows 出站翻译与生命周期回归。最后执行 typecheck、build 及打包脚本规定的完整检查。

### 10.2 真实客户端复测

由用户主动安装后，使用同一官方版本、同一会话数据规模、同一窗口尺寸与动作脚本做更新前后对照。记录每段 PID、renderer/target ID、bundle 哈希、内存压力、swap 和采集配置。每次重启可产生新 PID；单段中途更换 renderer 或采集丢失时，拆段记录，不合并为一组可比数据。

至少三轮覆盖冷启动、登录后空闲、中文输入、长草稿、选中复制、粘贴、长聊天滚动、快速切会话、首次及再次订单查询。每轮每类关键操作至少 30 次；不足以稳定估计高分位时增加样本，并报告样本量。常规压力和内存警告状态分组，不能用关闭其他应用后的结果与高压基线直接比较。

测量输入排队、事件处理和后续呈现分别花费的时间；滚动使用帧间隔与掉帧情况；会话切换测点击到目标内容可见。Event Timing 有最小阈值时同时记录支持范围与未覆盖事件，采用可比的帧/动作测量补充，不能把过滤后的分布称为全量 p95。记录助手 CPU、长任务来源、DOM/iframe/监听器数量和 60 分钟固定负载下的内存走势。

测量口径在对照前固定：

- 助手同步回调按订单观察、摘要定位、语言识别、输入快照、状态渲染和资源清理分别统计，纳入各自完整调用链，不以采样中的 self 时间代替回调时长。挂载、首次订单初始化单列，仍检查是否产生助手长任务。远端 TSIM SPA 执行单列，同时保留其对端到端响应的影响，不能因延后到点击才启动而从整体成本中消失。
- 60 分钟资源测试分为 10 分钟预热、40 分钟固定重复动作、10 分钟停止操作；每 5 秒记录主 renderer 的 JS heap/DOM 数、助手各进程 RSS，以及系统内存压力。第 5–10 分钟与第 55–60 分钟保持同一页面状态、会话规模和已释放工作台状态，比较中位数；不手动强制 GC。
- 初始资源门禁建议：上述各内存指标的末段中位数增量不超过基线的 10% 与 32 MiB 两者较大值；固定负载后 20 分钟的线性拟合增长斜率不超过 1 MiB/分钟。门槛需在正式对照前确定并记录，不能看到结果后再放宽；超限即保留未通过，区分官方与助手来源继续分析。通过仅说明这段负载观察稳定，不证明长期无泄漏。
- 助手监听器、observer、timer 和 iframe 通过测试构建的资源注册/释放计数核对；结束回到相同状态时应回到基线计数，缓存不得突破配置容量。无法直接观测的资源明确标为未验证，不能写“没有累积”。

以下为待验证的目标，尚非已实现结果：

| 层面 | 验收要求 |
| --- | --- |
| 翻译功能 | 旧、新请求模型均通过；真实用户翻译成功；无重复请求；422 不再误报连接失败 |
| 助手交互开销 | 指定动作集内无可归因于助手的大于 50 毫秒长任务，包含挂载及首次初始化；前述常规回调按类别分别以 p95 小于 8 毫秒、p99 小于 16 毫秒为目标，样本不足时报告最大值及次数；远端页面初始化成本独立报告 |
| 空闲开销 | 未查询不创建完整工作台；几何/订单/原文不变时不重复执行重扫描；资源释放符合约定 |
| 输入与复制体验 | 常规压力下，输入/复制响应目标 p95 不超过 100 毫秒、p99 不超过 200 毫秒；指标定义及系统剪贴板时间须明确，不能只测同步 handler |
| 滚动与会话切换 | 滚动记录 16.7/33.3 毫秒以上帧占比；本地会话切换目标 p95 不超过 300 毫秒，网络加载另报；仍有大于 500 毫秒阻塞须逐项归因并列为未关闭问题 |
| 资源稳定性 | 按上述 60 分钟口径核验内存中位数与增长斜率；助手资源计数回到相同状态的基线，缓存有界；指标超限或资源不可观测时保留未通过/未验证，不能用一次 RSS 下降宣称无泄漏 |
| 安全与正确性 | 无丢字、误发、跨会话替换、旧订单闪现、越权查询、登录态泄露或错误响应敏感数据外露 |
| 安装交付 | 同包组件版本一致，真实加载哈希可核对；隔离安装、更新、中断恢复及卸载恢复通过；用户主动安装后完成实机确认 |

这些体验目标受官方页面影响。目标未达成时必须保留未达成状态；助手可控门禁通过只允许报告助手侧修复通过，不允许报告“全部卡顿已解决”。复测过程需要浏览器操作时，统一通过 `ego-browser` 执行和取证。

## 11. 实施顺序与最终交付清单

1. 固化脱敏基线与运行时版本；保留现有未提交改动，划清本修复新增范围。
2. 并行实施两个独立工作项：翻译白名单/TSIM 错误展示；工作台按需加载与释放。各自通过行为测试。
3. 实施订单扫描和摘要布局优化，再做语言缓存及经测量必要的输入优化。共享页面入口的修改串行整合。
4. 完成接口兼容、权限/会话隔离和真实页面性能的独立复核，检查所有用户可见术语为 TSIM。
5. 统一构建一个候选注入包，在临时目录完成安装事务验证；交付校验和、简明安装说明和验收报告。
6. 用户在安装器主动更新后完成真实操作复测；将通过项、未通过项和官方侧剩余问题写入同一报告，再决定是否可正式发布。

最终应提供：本计划对应的代码与回归测试、一个 macOS 注入安装包、构建及签名信息、更新前后可比性能结果、翻译兼容结果、恢复说明，以及仍无法由助手解决的问题清单。当前代码、回归与候选包已完成；真实客户端对照、在线翻译及长时资源验收仍待用户主动安装后执行，不能提前标记通过。
